# 报修处理流程

1. 学生或宿舍长提交报修，获得工单编号，页面显示“待派单”。报修人收到回执；管理员及该楼栋宿管收到派单待办。
2. 管理员或负责该楼栋的宿管打开“报修工单”，点击“查看待派单工单”，在对应行点击“派单给维修人员”，选择启用的维修账号并提交。
3. 被指定的维修人员打开“我的维修工单”，刷新后可看到该记录；其他维修人员无法查看或操作。报修人收到派单通知。
4. 维修人员依次点击“开始处理”“提交验收”，填写实际完成说明。
5. 报修人或本宿舍当前宿舍长验收。通过后工单变为“已完成”，未通过则退回“处理中”。

“待处理”是维修进度，“待派单/已派单”是责任分配状态。学生提交不代表已派到某个维修账号。
维修端列表为空时，先确认是否已经派给当前账号，再清除筛选并刷新。多账号体验建议使用不同浏览器或隐私窗口，避免同一浏览器共享登录 Cookie。

历史待处理工单也可在待派单筛选中找到，无需重复报修。系统不会自动改派历史工单。

## 自动优先级

提交报修时，后端按本地规则自动判断“普通 / 紧急”，回执、工单列表和派单待办展示判断结果与依据。
漏电、冒烟、火花、燃气泄漏、爆管、污水倒灌、人员被困及全宿舍停电等特征建议优先核实处理。
支持“没有漏电”“未发现冒烟”等常见紧邻否定；复杂表述、图片内容及未列入规则的风险仍需工作人员判断。
未命中特征并不代表没有风险，该规则仅用于分流，不替代现场核实。无需配置 API，也不会向 DeepSeek 发送报修描述。

派单默认“自动判断”，管理员 / 宿管可改选“普通”或“紧急”，派单说明作为人工调整理由保存到处理记录及审计。
人工调整后改派会默认保留人工级别；选择“自动判断”可恢复规则建议。普通或紧急均不自动分配维修人员。
未完成工单优先于待验收、已完成工单；同一阶段组中紧急优先，同级按提交时间从早到晚排序。
工单 Excel 导出包含实际优先级、自动建议、来源及依据。

升级时会补算已有未派单的待处理工单，保留已派单或已处理工单的原优先级。
判断依据存入独立的 `repair_priority` 表，兼容 MySQL / SQLite，不需要为应用账号增加 ALTER 权限。

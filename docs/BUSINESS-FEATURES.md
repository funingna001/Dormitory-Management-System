# 宿舍业务功能与验收说明

后端为 **Spring Boot 4.0.9 + Spring Security + JDBC**，数据库默认本机 MySQL；前端为独立 **Vue 3 + Vite**，通过 `/api/**` 调用后端。Spring Boot 用于后端服务，不代替浏览器端 Vue。

本次依据用户对全部 15 项功能的确认实现。收费采用账单与经核实的线下缴费、退款登记；通知采用站内公告和个人消息；访客、晚归采用人工登记。未接入真实支付、短信、门禁硬件或外部财务系统，不会自动扣费或向外部人员发送消息。

## 功能对应表

| 编号 | 功能 | 页面与实际行为 |
| --- | --- | --- |
| 1 | 具体床位 | 床位管理；房间容量生成编号床位，支持空闲、占用、预留、停用，预留可指定学生和到期时间，入住关联到具体床位 |
| 2 | 入住 / 调宿 / 退宿 | 学生提交申请，管理员、宿管或负责辅导员审核；批准后预留目标床位，管理员或目标宿管实际办理；调宿在同一事务释放原床位并占用新床位，校验过期、变更和重复办理 |
| 3 | 住宿历史与归档 | 保留入住和退宿时间、分别记录原因与经办人；毕业、休学、退学归档并停用账号；学生记录、历史和费用流水不会硬删除 |
| 4 | 房间可用状态 | 正常、维修、关闭；停用房间仍可保存现有住户和办理移出，但旧接口、新接口和批量分配都不能向其安排新入住 |
| 5 | 宿管职责范围 | 新增宿管与辅导员角色；宿管按楼栋授权，辅导员按学生档案的负责关系审核；维修人员仅访问派给自己的工单；前端菜单与后端权限同时限制 |
| 6 | 完整报修 | 管理员或宿管派单 / 改派、优先级、维修开始、完成说明、学生验收或退回重修、评价、完整事件记录；同寝室成员可查看公共报修，报修人或宿舍长验收 |
| 7 | 宿舍长任命 | 管理员或本楼宿管明确任命已入住成员，记录任命、离任与原因；入住人员变化不再按学号自动改选 |
| 8 | 账号维护与操作记录 | 自助修改密码、管理员重置、启用停用、初始密码强制修改、凭据版本撤销其他会话；为缺少账号的旧学生档案补建账号；重要操作记录主体、对象、时间与说明，密码不进入审计详情 |
| 9 | 通知与待办 | 全校或指定楼栋公告、已读记录；住宿审批、维修、费用、检查和资产操作产生个人站内消息，消息按收件人隔离 |
| 10 | 假期留宿 / 外宿 / 晚归 | 类型、起止时间、申请原因、联系号码、审批与实际结束 / 返校登记；限制时间范围和重复重叠申请 |
| 11 | 访客 | 宿管登记真实被访学生与宿舍关系、访客联系信息、进入与预计离开时间，并登记实际离开；学生只能看自己的访客 |
| 12 | 卫生与安全 | 检查类型、评分、具体检查项目 / 问题、照片、整改期限、整改说明与照片、复查通过或退回；图片按宿舍范围鉴权，关闭后的检查图片不可修改 |
| 13 | 住宿 / 水电 / 赔偿费用 | 单人账单或按当前住户分摊，整数分保存金额并处理尾差；管理员登记缴费、退款与唯一凭据号，禁止超收、超退和重复流水；学生仅查看本人账单，欠费可阻止退宿 |
| 14 | 家具 / 设备 / 钥匙 | 独立资产编号、类别、所在房间、领用学生、归还、损坏、遗失、维修和报废状态；领用对象必须住在该宿舍，未交接物品可阻止退宿 |
| 15 | 批量导入与分配 | 下载 XLSX 模板，校验后生成 15 分钟预览，再整批确认；密码只保存哈希、不返回预览；分配按性别、楼栋和可用床位筛选，优先同学院、年级和班级，确认时重新校验版本并防止重复执行 |

## 角色使用顺序

1. 使用现有管理员登录，先在“修改密码”设置强密码。
2. 在“账号与楼栋权限”创建宿管、辅导员、维修人员。宿管指定负责楼栋；新账号首次登录先修改初始密码。
3. 在“学籍与住宿档案”填写学院、专业、负责辅导员；旧学生没有账号时可点击“开通学生账号”。不会自动替 432 个学生生成公开的统一弱密码。
4. 宿舍长通过“宿舍长任命与交接”指定，不再随学号变化自动重选。
5. 旧报修工单保留，管理员先派给维修人员；维修人员提交验收后，由报修人或当前宿舍长确认完成。
6. 学生的入住、调宿与退宿从申请页面提交；管理员仍可直接安排合法入住。所有路径共用性别、容量、可用状态、床位及交接校验。

## 可配置规则

“住宿业务规则”提供三个明确开关：退宿 / 跨宿舍调整前结清费用、完成物品交接、允许所有已入住学生报修。默认均开启；关闭“允许所有已入住学生报修”后仅宿舍长可提交。

审批通过不等于已搬入或已退宿，须完成“办理完成”。预留默认三天；管理员也可显式指定未来 30 天内的预留截止时间。过期床位在查询或分配前重新检查释放。其他学校特定审批链、收费标准和门禁时间没有作为通用校规擅自写死，当前由有权限的人员登记与审核。

## 数据升级

升级采用 24 张独立业务表，保留原有五张表和原主键。应用启动后为已有房间补建床位，并按当前实际入住创建一次接入历史；接入时间表示“原系统记录接入”，不伪造学生真实历史入住日期。原宿舍长保留并产生接入记录。重复启动不重复生成床位或开放住宿历史。

升级前备份位于 `backups/before-business-features-20261028-095120/`，包含 MySQL SQL 快照与源码压缩包。原 SQLite 文件仍保留；正式业务默认写入 MySQL。

## 验证与安全边界

- 自动化覆盖全部 15 项模块及原有业务：临时 SQLite、隔离 MySQL 各执行 51 项集成测试，全部通过；测试代码拒绝对正式库运行清空式测试夹具。
- 浏览器验证五种角色、19 个业务页面、17 个连续业务场景，包括欠费和钥匙阻断退宿、处理完毕后完成退宿、归档、导入、分配和强制改密。结果见 `artifacts/business-browser-result.json`。
- 重要安全检查：跨楼栋、跨学生、未派单维修、个人消息与照片权限、CSRF、字段注入、账号失效、密码不进日志、缴费并发、批次归属与失效、压缩包展开限制、公式拦截、图片真实格式与像素 / 并发限制、JSON 体积限制。
- 依赖审计使用 npm audit 和 OSV 已公开漏洞库，不能证明不存在未知漏洞。验收记录见 `artifacts/mysql-integration-tests.log`、`artifacts/business-final-build.log`、`artifacts/backend-osv-audit.json`。
- 2026-10-28 正式 MySQL 升级验收：29 张表、150 间宿舍、752 个床位、431 个占用床位与开放住宿记录，悬空占用为零。原有五张表逐行校验通过（仅保留先前批准的六人间容量调整），原 SQLite 与备份一致。实际服务登录、16 个新业务查询接口、附件、统计、Excel 导出及退出通过验证；测试库已清理。

真实支付、短信和门禁接入需要各自系统的凭据及接口约定，当前界面会明确以登记或站内消息呈现，不会宣称已经完成外部系统核验。
